- 상태: **1차 검토 완료. 제품 코드 수정, 파일 삭제, 커밋/푸시는 하지 않음.**

## 1. 먼저 고칠 문제

P1은 데이터 신뢰성/실행 안정성에 직접 영향을 주므로 구조 정리보다 우선한다. P2는 유지보수, 배포 재현성, 검증 범위와 성능 개선 항목이다. 아래에서 재현 결과와 코드상 위험을 구분한다.

### R1. P1: EDFA 상태 확인이 DMA 수집을 막을 수 있음

**근거:** `src/drivers/edfa/edfa_serial_controller.cpp:23`, `:103`, `:238`; `src/core/acquisition_session.cpp:263`.

`pollStatus()`는 `mutex_`를 잡고 UART 응답까지 기다린다. `status()`도 같은 잠금을 사용한다. 별도 EDFA monitor 스레드가 있어도, DMA 수집 스레드의 `waitForBatch()`가 `edfa_.status()`를 호출하므로 이 대기가 수집 경로로 전파된다.

모의 serial transport에서 응답을 150 ms 지연시킨 결과:

```text
injected_serial_delay_ms=150 status_blocked_ms=167.417 telemetry_valid=0
```

상태 조회가 지연된다는 점은 재현했다. 그 지연이 특정 장비에서 실제 overflow를 만드는지는 별도의 장시간 DMA 시험이 필요하다. 과거 전원 재부팅으로 해결된 Jetson overflow의 원인이라고 단정하지 않는다.

**수정 방향:** UART 명령 직렬화용 잠금과 상태 스냅샷용 잠금을 분리한다. I/O는 잠금 분리 후 실행하고, 성공/실패 결과만 짧게 상태에 반영한다. 수집은 마지막 확인 상태와 갱신 시각만 읽는다. 통신 실패 시 정지 정책은 유지한다.

**완료 기준:** 150~500 ms 응답 지연/timeout을 주입해도 `status()`가 UART 완료를 기다리지 않고, 수집 진행과 오류 보고가 모두 유지됨.

### R2. P1: 저장 큐 overflow인데 완료 파일로 기록될 수 있음

**근거:** `src/storage/async_storage_service.cpp:31`, `:138`, `:168`, `:321`; `src/storage/binary_storage.cpp:178`.

큐 overflow는 `failed=true`를 설정하지만 `worker_error`는 비어 있다. `finalizeOptions()`는 `worker_error.empty()`만 보고 `completed`를 만든다. 따라서 저장을 놓쳤는데도 메타데이터는 완료로 표시할 수 있다.

큐 크기 1과 잠시 멈추는 모의 writer로 재현한 결과:

```text
second_accepted=true third_overflow=true storage_failed=true
finalized_completed=true wait_succeeded=true
reason=Raw storage queue capacity exceeded
```

`waitUntilStopped()`의 성공은 worker 정리 성공이라는 의미일 수도 있다. 하지만 이를 측정/저장 성공과 구분하지 않고 `completed=true`로 남기는 것은 데이터 해석을 잘못하게 만든다.

**수정 방향:** 정리 완료, 정상 측정 종료, 누락 없는 저장 완료를 구분한다. 최종 세션 결과에 overflow/쓰기 실패/최종화 실패를 모두 포함하고, raw/point-cloud writer가 같은 결과를 기록하도록 한다.

**완료 기준:** raw 및 point-cloud 큐 overflow, 디스크 쓰기 실패, finalize 실패를 각각 주입했을 때 부분 데이터는 보존하면서 최종 상태/메타데이터는 실패를 명확히 기록함.

### R3. P1: Stop 실패가 성공 안내에 가려질 수 있음

**근거:** `src/apps/common/application_controller.cpp:342`, `:350`, `:1080`, `:1160`, `:1191`.

`stopProcessing()`과 `stopStorage()`는 종료 대기의 결과/error를 상위로 전달하지 않는다. `stopRuntime()`의 최종 상태는 주로 하드웨어 종료 error에 의해 결정되고, 저장 최종화가 실패해도 `Storage finalized` 로그를 남길 수 있다. `stopRuntimeCommand()`도 종료 결과와 무관하게 `Acquisition stopped cleanly`를 알린다. Emergency stop 역시 실제 실패와 무관한 `All runtime outputs stopped` 안내가 있다.

**수정 방향:** 단계별 결과를 모은 `StopResult`를 반환한다. 성공/실패 이벤트, 화면 상태, 세션 메타데이터가 같은 결과를 사용하도록 한다. 출력 차단 명령을 보낸 것과 장치가 차단을 확인한 것은 구분한다.

**추가 위험:** E-stop은 `ApplicationController::emergencyStop()`의 queued 호출이다(`:1616`). 같은 runtime 스레드의 동기 waveform upload나 `AcquisitionSession::arm()`의 EDFA warm-up 대기가 끝나야 처리될 수 있다(`src/core/acquisition_session.cpp:125`). 이 경로는 취소 가능한 작업으로 바꾸고 최악 응답 시간을 별도로 검증해야 한다. 실제 장치 차단 시간은 이번에 측정하지 않았다.

**완료 기준:** 각 종료 단계 실패가 UI/로그/파일에 동일하게 남고, 업로드/arm 도중 정지 요청도 처리됨. 소프트웨어 E-stop을 별도 하드웨어 안전장치와 동일하게 설명하지 않음.

### R4. P1: 기록 도중 바꾼 Processing 설정은 raw 재생으로 복원되지 않음

**근거:** `src/apps/common/application_controller.cpp:199`, `:376`; `src/storage/writer_interfaces.h:24`; `src/storage/binary_storage.cpp:200`, `:442`; `docs/data_contract.md:53`.

기록 시작 시 전체 설정과 업로드한 waveform을 보관하는 경로는 있다. 그러나 실행 중 peak threshold/DC removal 등을 바꾸면 processing revision만 진행되고, 그 revision에 해당하는 설정 내용과 실제 적용 시작 지점은 저장하지 않는다. point-cloud frame에 revision 번호가 있어도 이를 설정으로 해석할 이력이 없다. 문서에는 이미 revision history가 저장된다고 쓰여 있어 구현과도 다르다.

예를 들어 raw 기록 중 threshold를 바꾸면, 현재 replay는 시작 설정을 불러올 수 있지만 당시의 설정 변경 순서까지 재현할 수 없다. 원시 ADC 데이터 자체의 손상이라는 뜻은 아니다.

**수정 방향:** 처리 worker가 새 설정을 실제 적용한 프레임 경계에서 `{revision, effective source boundary, processing config}` 이벤트를 만든다. 저장/재생이 이 이벤트를 사용하도록 하고, 사용자가 재생 설정을 덮어쓸 때는 원본 재현과 구분한다.

**완료 기준:** 기록 중 threshold 변경 전후의 유효점/거리/XYZIV 결과를 같은 revision 경계로 재생할 수 있음. 기존 파일은 시작 설정만 있는 포맷으로 계속 읽을 수 있음.

### R5. P2: 빌드 성공과 실제 배포 기능이 일치하지 않음

**근거:** `src/CMakeLists.txt:118`, `:160`; 현재 두 Windows build cache; `build/package/FMCW_LiDAR_Jetson_Source/SOURCE_REVISION.txt`.

일반 Windows 구성은 Alazar/FFTW/CUDA가 있고 CenterPoint는 OFF다. 별도 CenterPoint 구성은 CenterPoint/CUDA가 있지만 이번 구성 확인에서 Alazar/FFTW 의존성이 발견되지 않아 해당 실제 backend가 빠진 상태다. `WITH_* = ON`이라는 요청만으로 실제 기능 포함을 보장하지 못한다.

CenterPoint 증분 빌드는 성공했지만 `fmcw_detection_input_tests`는 실행 시 `0xc0000135`로 실패했다. cache에 남은 cuDNN runtime 경로는 실제 파일이 없고 runtime DLL 목록도 비어 있다. 로더 단계 의존성 문제를 먼저 해결해야 하며, 증분 링크 성공을 배포 실행 성공으로 볼 수 없다. 정확히 어떤 종속 DLL이 처음 실패했는지는 추가 loader 진단 대상이다.

로컬 Jetson 소스 배포본의 revision은 `09541fcc...-dirty`로, 현재 HEAD `5f630b9`와 다르다. 대표 파일 비교에서도 controller/UI/replay/tests가 현재 소스와 달랐다. 이는 **이 PC에 보관된 배포본**에 대한 확인이며, Jetson에서 실제 실행 중인 파일의 버전을 이번에 확인한 것은 아니다.

**수정 방향:** 지원하는 빌드 기능 조합을 명시하고 필요한 backend가 빠지면 배포 빌드를 실패시킨다. cache 문자열뿐 아니라 파일 존재와 runtime 의존성을 검사한다. 패키지마다 commit, dirty 여부, Qt/CUDA/SDK 버전, 실제 포함 기능을 기록한다. Windows 실행 패키지와 Jetson source export는 같은 revision으로 만든다.

**완료 기준:** 개발 PC의 PATH에 기대지 않는 새 패키지 폴더에서 시작/기능 확인 성공. Jetson 배포 소스 manifest와 승인된 commit 일치.

### R6. P2: 테스트한 상태 정책과 실제 앱 상태 정책이 따로 있음

**근거:** `src/core/config_manager.cpp:49`, `src/core/config_policy.cpp:16`, `src/core/operation_controller.cpp:21`; `tests/config_system_test.cpp:425`; `src/apps/common/application_controller.cpp:52`.

`ConfigManager`, `OperationController`는 core에 컴파일되고 테스트도 있지만, 현재 앱에서 직접 사용하는 호출 경로는 확인되지 않았다. 실제 설정 적용/상태 전이는 `RuntimeWorker`와 `MainWindow`가 별도로 구현한다. 따라서 이 core 정책 테스트가 통과해도 GUI Apply/Start/Stop 동작이 검증됐다고 볼 수 없다.

**수정 방향:** 실제 runtime의 상태/설정 전이를 테스트 가능한 대상으로 먼저 추출한다. 그다음 기존 정책 구현을 통합하거나 사용하지 않는 초기 구현으로 분류한다. 오래된 core 구현에 실제 앱을 무조건 연결하는 방식은 피한다.

**완료 기준:** 단일 정책을 GUI와 회귀 테스트가 같이 사용함. scanner 무관 Apply의 waveform 보존, upload 중 Start 금지, Stop 후 재시작, 장치 연결 실패 복구를 실제 orchestration 경로로 테스트함.

### R7. P2: UDP가 꺼져도 A-scan마다 동적 할당함

**근거:** `src/apps/common/application_controller.cpp:244`; `src/processing/processing_service.cpp:224`; `src/network/udp_sender_service.cpp:211`.

앱은 UDP OFF여도 non-empty processed callback을 설치한다. 처리 worker는 그 callback이 있으면 매 A-scan 결과에 `make_shared<ProcessedFrame>`을 실행한다. 998 records x 200 batches/s에서는 이 경로만 초당 199,600회에 해당한다. 이번에 이를 실제 성능 저하의 주원인으로 계측한 것은 아니지만, UDP OFF일 때 불필요한 작업인 점은 명확하다.

UDP는 A-scan 결과로 별도 frame 조립도 수행한다. 화면/저장이 사용하는 완성 `PointCloudSnapshot`과 다른 조립 규칙을 유지하므로 frame 경계와 누락 처리의 일관성을 별도로 검증해야 한다.

**수정 방향:** 최소 수정은 UDP OFF 시 callback을 설치하지 않는 것이다. 이후에는 완성 frame을 표시/저장/UDP가 공유하고 송신 전용 worker에서 packet 변환하게 정리한다.

**완료 기준:** UDP OFF일 때 위 per-record 할당 제거. UDP ON/OFF 결과 동일성, 누락/정지 중 frame 경계, queue 상태와 처리 latency 회귀 확인.

### R8. P2: Jetson CUDA 전용 구성에서 중요한 실시간 테스트가 빠짐

**근거:** `tests/CMakeLists.txt:181`.

end-to-end realtime probe/600초 acceptance target과 일부 storage tests가 `FMCW_HAS_FFTW` 조건 안에 있다. FFTW를 끈 Jetson은 별도 CUDA 처리 성능 테스트가 있어도, 그 테스트가 동일한 200 Hz 수집/큐/저장 검증을 대체하지는 않는다.

**수정 방향:** 테스트를 CPU 라이브러리 존재가 아닌 검증 기능별로 구성한다. 공통 realtime harness는 CUDA만 있어도 빌드하고, backend에 맞게 실행한다. 기존 `phase4`, `phase7` 이름은 실행 책임이 드러나는 이름으로 점진 변경한다.

**완료 기준:** Windows FFTW, Windows CUDA, Jetson CUDA 각각 실제 지원 항목의 테스트 목록을 확인할 수 있고, 빠진 테스트를 명시함.

### R9. P2: UI에 파일 해석과 전체 로그 재작성 작업이 남아 있음

**근거:** `src/apps/common/main_window.cpp:654`, `:711`, `:3458`.

point-cloud replay의 `open()`/`readNext()`가 GUI 스레드에서 실행된다. 큰 ASCII/PCD frame 해석이 오래 걸리면 renderer가 빨라도 UI가 멈출 수 있다. 로그도 한 줄 추가할 때 최대 2,000줄을 필터링해 `setPlainText()`로 다시 만들며 자동으로 마지막으로 스크롤한다.

**수정 방향:** replay 읽기는 취소 가능한 worker와 제한된 사전 읽기 큐로 옮긴다. 로그는 추가분 중심으로 갱신하고 사용자가 과거 로그를 읽는 동안 스크롤을 보존한다. `storage/point_cloud_replay.cpp`와 `detection/point_cloud_file_loader.cpp`의 PCD 해석도 공통 reader + detection 입력 변환으로 정리할 후보이다.

**완료 기준:** 큰 파일/빠른 로그 입력에서도 버튼 응답 유지, 파일 교체/중단 시 이전 frame 미유입, XYZ/XYZI/XYZIV의 각 입력 규약 유지.

### R10. P2: 시간/프레임/설정 용어에 단일 기준이 부족함

**근거:** `src/processing/processing_service.cpp:21`, `:777`; `src/core/frame_types.h:99`, `:260`, `:307`, `:340`; `src/core/config_policy.cpp:19`.

batch deadline은 고정 5 ms다. 200 Hz 기준 성능 목표로는 유효하지만 사용자 100 Hz 설정의 현재 deadline과 같은 뜻으로 표시하면 오해를 만든다. 레이저 sweep rate만으로 B-trigger 간격을 정하면 안 된다. 기준 workload 목표, 실제 batch 입력 간격, queue 여유, frame FPS, paint Hz를 구분해야 한다.

`RawFrame`/`ProcessedFrame`은 A-scan 하나이고 `PointCloudSnapshot`은 완성 raster frame이다. `PointXYZI`에는 velocity와 추가 provenance 필드도 있다. `x_angle_deg`는 방위각이지 waveform 원본 X열이라는 뜻이 아니다. 이러한 명칭이 과거 좌표계/프레임 논의를 반복하게 만드는 요인이다.

`ui.segment_overlay`, `ui.color_map`처럼 profile codec/정책에는 있지만 실제 화면 반영 경로가 확인되지 않은 항목도 있다. `a_scan_count`/`records_per_buffer`, `x_pixel_count` 등 동기화되는 설정도 원본 값과 파생값을 구분해야 한다.

**수정 방향:** 먼저 용어/단위/설정 정책표를 만든다. 그 후 내부 명칭을 개선하되 기존 raw/UDP/config 필드와 포맷 호환성은 adapter 또는 schema migration으로 유지한다. 설정 키는 쓰지 않는다는 이유만으로 바로 삭제하지 않는다.

## 3. 실제 데이터를 따라 읽는 순서

```text
MainWindow controls
  -> ApplicationController (Qt queued commands)
  -> RuntimeWorker (configure/connect/start/stop orchestration)
  -> AcquisitionSession + ContinuousAcquisitionWorker
  -> Alazar / Simulator / Raw Replay digitizer
  -> RawFrameBatch + scan/config/optical metadata
       -> AsyncStorageService -> raw + setup/waveform metadata
       -> ProcessingService queue
          -> CPU FFTW or CUDA signal pipeline

  -> PointCloudReplayReader (currently called by GUI)
  -> already processed PointCloudSnapshot -> display / optional detection
```

### 현재 코드에서 확인한 기준

- `RawFrame` 1개는 한 chirp record/A-scan이다. `RawFrameBatch`는 DMA 묶음이다. 현재 표준 scan 설정에서는 한 batch가 한 B-scan line에 대응한다.
- Time Domain/FFT는 selected A-scan 표시다. 전체 A-scan 신호처리는 batch 단위로 진행하며, 표시용 선택과 연산 대상 선택은 다르다.
- `bidirectional` ON 시 홀수 line의 record를 공간 X index에 역순 매핑한다. A-scan 내부의 시간 samples를 뒤집어 FFT하는 것이 아니다.
- elevation은 들어오는 line 순서에 대해 end에서 start 방향으로 계산한다. 설정이 -2~+2도라면 첫 line +2도, 마지막 line -2도다.
- 출력 좌표는 +X 전방, +Y 좌측, +Z 위쪽이다. 스캐너의 실제 X/Y 명령열과는 별개다.
- threshold 이하 peak는 invalid다. 유효한 peak에 대해서만 승인된 3점 dB 포물선 보정을 사용한다. 초기 대화의 '보간 없음'을 현재 규칙으로 되돌리면 안 된다.
- raw replay는 ADC를 다시 처리하는 경로이고, point-cloud replay는 이미 계산된 점을 읽는 경로다.
- CPU/CUDA 별도 구현, simulator, backend OFF용 stub은 필요한 코드다. 비슷해 보인다는 이유로 삭제하지 않는다.

### 함수 설명 양식: 목록보다 실제 계약을 설명하기

각 핵심 함수는 `호출자 -> 입력/단위 -> 조건 -> 연산 -> 출력 -> 소유권/스레드 -> 실패/부작용 -> 테스트` 순서로 설명한다. 이름에서 추측한 일반 문장을 붙이지 않는다.

예: `src/processing/signal_processor.cpp`의 `toPoint()`는 `finalizeMeasurement()`에서 호출된다. 거리(m), 방사속도(m/s), intensity(dB), 방위각/고도각(deg), 보정 각도(deg)를 받아 다음을 계산한다.

```text
azimuth = (x_angle_deg + x_angle_offset_deg) * pi / 180
elevation = (y_angle_deg + y_angle_offset_deg) * pi / 180
x = distance * cos(elevation) * cos(azimuth)
y = distance * cos(elevation) * sin(azimuth)
z = distance * sin(elevation)
```

유효하지 않은 입력은 기본 invalid/NaN point로 반환한다. 유효하면 XYZIV와 원본 scanner 명령값을 채운다. 파일 저장/UI/장치 I/O는 하지 않는다. CUDA의 대응 계산은 `cuda_signal_pipeline.cu`에도 있으므로 축 방향/부호 회귀 테스트를 둘 다 유지해야 한다.

이전에 만든 함수 사전 생성기의 `return_description()`/`processing_description()`에는 이름/반환형 기반 일반 설명이 포함되어 있다(`tools/generate_source_reference.py:1289`, `:1304`). 예를 들어 모든 bool을 성공/실패로 설명하면 조건 판정 함수의 의미를 잘못 전달한다. 현재 자료형과 다른 `PointCloudPoint` 명칭도 남아 있다. **이 문서는 검색 색인으로 유용하지만, 모든 함수의 동작/실패 정리를 검증한 명세는 아니다.** 이 부분은 새 설명서를 늘리기 전에 고쳐야 한다.

문서의 권장 체계는 다음 네 가지다. 폴더 이동은 아직 하지 않았다.

1. 현재 시작점: 빌드/실행/소스 읽는 순서와 현재 지원 기능.
2. 단일 규약: 설정 적용 정책, 데이터 단위/좌표계, 저장/통신 버전.
3. 결정 이력: 날짜별 검토/phase/handoff. 현재 구현 여부를 표시.
4. 참고 색인: 파일/함수 검색용 목록. 실제 설명은 호출 흐름별 문서로 연결.
